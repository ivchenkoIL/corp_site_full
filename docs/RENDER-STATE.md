## 1. Чем и как мерялось

Оснастка — в `games/montazh-city-3d/tools/`, подробности и все ключи в
`tools/README.md`:

| Файл | Что делает |
| --- | --- |
| `mac-baseline.sh` | Снимает всё одной командой: ставит недостающее, гоняет три сцены в двух браузерах, складывает сравнительную таблицу |
| `perf-inject.js` | Ставится в страницу **до** загрузки игры. Считает draw call'ы и треугольники по проходам, память под текстуры (включая массивы слоёв и sized-форматы) и буферы, время кадра, время GPU таймер-запросами, размер буфера отрисовки, границы фаз загрузки. Игру не правит ни строчкой |
| `perf-probe.mjs` | Гоняет три сцены в Playwright, снимает метрики и скриншоты, кладёт JSON в `docs/perf/`. Ключи `--quality` и `--dynamic` задают профиль и авто-масштаб |
| `perf-trace.mjs` | Сэмплирующий профилировщик V8 через CDP |
| `scenes.mjs` | Три контрольные сцены, файл сохранения и настройки — общий модуль для probe, trace и shot |
| `shot.mjs` | Снимок сцены за пятнадцать секунд с проверкой ошибок страницы, `gl.getError`, фаз загрузки по заданиям и памяти; точка и час — свои |
| `shot-stats.mjs` | Яркость и контраст кадра по полосам, монтаж «до \| после», без зависимостей |
| `compare.mjs` | Сводит два прогона в одну таблицу |
| `cull-check.mjs` | Проверяет, что отсев по клеткам консервативен: рисует кадр дважды ВНУТРИ одного кадра, с отсевом и без, и сравнивает попиксельно |
| `fx-check.mjs` | То же для эффектов: кадр с эффектом и без ВНУТРИ одного кадра, три PNG («с», «без», усиленная разность») и доля тронутых пикселей. `--fx=bloom \| ssr \| ssaoblur` |
| `profile-check.mjs` | Переключение качества на лету настоящим путём: открывает настройки и жмёт ту же кнопку «Качество», что и игрок, после каждого нажатия рисует кадр и проверяет `gl.getError` |
| `shadow-check.mjs` | Две проверки теней счётом: `--stab` — не дрожат ли каскады при сдвиге камеры, `--bias` — окно смещения между рябью и отрывом тени |
| `ext-probe.js` | Снимок возможностей WebGL2 для консоли настоящего Safari |
| `find-playwright.mjs` | Ищет playwright по всем обычным местам |
| `toc.mjs` | Пересобирает оглавление в начале `index.html`. `--check` — проверка без записи |

Перезамерить целиком — одна команда **из папки игры**:

```bash
cd <клон репозитория>/games/montazh-city-3d
bash tools/mac-baseline.sh          # база в двух браузерах, минут десять
node tools/perf-probe.mjs --scene=all --warmup=12 --measure=40 --profile=15 \
     --minFrames=60 --width=1440 --height=900 --dpr=2 --quality=medium \
     --shots=docs/shots/01-textures --out=docs/perf/01-textures-medium-chromium.json
node tools/compare.mjs docs/perf/00-base-mac-chromium.json \
     docs/perf/01-textures-medium-chromium.json --out=docs/perf/01-compare-medium.md
node tools/shot.mjs --scene=dense --quality=high --out=/tmp/dense.png   # быстрая проверка
node tools/toc.mjs --check
```

Три вещи, которые оснастка делает ради повторяемости:

* **Math.random посеян фиксированно**, иначе жители расставляются по-разному.
* **Сцена задаётся штатным сохранением игры** в `localStorage`; профиль
  качества и авто-масштаб — штатными настройками (`…_opt`).
* **Кадры с открытым диалогом выбрасываются**; время кадра считается только
  между соседями по исходной последовательности.

И одна, о которой надо помнить с этапа 02: **авто-масштаб в замере
выключен** (`--dynamic=0` по умолчанию). Иначе игра сама держит кадр в
бюджете, FPS упирается в частоту монитора, а меняется разрешение — сравнивать
нечего. Пока `perf-inject.js` держит свой запрос таймера, игра свой не
открывает; с `--dynamic=1` авто-масштаб под оснасткой работает по интервалам
кадров, как в WebKit.

### Где мерялось

Все цифры в этом документе сняты на целевой машине:

```
Mac mini M4, 10 ядер, дисплей 4608×2592 («как 2304×1296», dpr 2, 60 Гц)
Chromium 151.0.7922.34 (Playwright) — ANGLE Metal Renderer: Apple M4
WebKit 26.5 (Playwright)            — Apple GPU
```

Headless-режим Playwright не привязан к развёртке монитора: интервалы rAF в
Chromium гуляют от 7 до 26 мс, и FPS «по медиане кадра» там — про
планировщик, а не про игру. Честная цифра для Chromium — **время GPU по
`EXT_disjoint_timer_query_webgl2`**; в WebKit расширения нет, и кадр там
честно зажат развёрткой 60 Гц (17 мс). Замер этапа 00 шёл в контейнере на
SwiftShader; его цифры остались в журнале и переносятся только по форме
нагрузки.

### Масштаб рендера и авто-масштаб

С этапа 03 сцена рисуется не в холст, а в собственный HDR-буфер, и масштаб
живёт на нём: `HDR = холст × GL.scale`, холст всегда в полной плотности
(`GL.w × min(dprMax, devicePixelRatio)`), в него пишет проход тонмаппинга.
Слой интерфейса (`#hud2d`, DOM, мини-игры) — в `min(2, devicePixelRatio)`, от
масштаба не зависит.

Мультисэмплинг тоже свой: `renderbufferStorageMultisample` плюс
`blitFramebuffer` в текстуру. У контекста `antialias` выключен — его
мультисэмпл разрешается в холст, а нужно в текстуру.

`Perf` (раздел 7) крутит `GL.scale`:

1. **Частота монитора** — медиана 48 интервалов rAF, прижатая к ближайшей из
   известных частот (в пределах 8 %), перемер каждые 15 с. Бюджет кадра —
   80 % интервала.
2. **Время GPU** — запрос `TIME_ELAPSED_EXT` вокруг всей работы кадра
   (`renderFrame`), результат читается без ожидания, когда готов; при
   `GPU_DISJOINT_EXT` ожидающие запросы выбрасываются.
3. **Пропуски** — интервал длиннее 1.5 бюджета; считаются долей за 60
   кадров. При живом таймере пропуск учитывается, только если GPU занят
   хотя бы наполовину.

Шаг вниз — после 4 кадров подряд сверх бюджета, шаг крупнее при перерасходе
(до ×3). Шаг вверх — после 1.5 с с запасом (GPU < 60 % бюджета); без
таймера — после 3 с без пропусков. Между шагами пауза 350 мс, масштаб на
сетке 0.025. После «вверх и сразу вниз» планка держится 8 с.

Проверено в headless Chromium: буфер 5120×3200 → масштаб 0.775 за 2 с;
уменьшение окна → возврат к 1.0 за 8 с (по шагу каждые ~2 с).

### Что применяется когда

| Сразу, в игре | При следующем запуске |
| --- | --- |
| плотность, масштаб, анизотропия, число источников, дальности, частицы, полоски развёртки, **мультисэмплинг** (свой буфер, а не атрибут контекста), **размер текстур** (пересборка с полосой прогресса) | плотность зелени (`VEG` зашит в геометрию района) — игра предупреждает тостом |

Настройки → «Качество: …» перебирает профили, «Авто-масштаб» включает и
выключает контроллер, строка под кнопками показывает буфер, масштаб,
частоту монитора, бюджет, время GPU, длину кадра и число шагов.

## 4. Текстуры

### Комплект карт

| Группа | Материалы | Слои | Формат | Что внутри |
| --- | --- | ---: | --- | --- |
| `surf` 512² | asphalt, road, sidewalk, panel, stucco, brick, indust, garage, roof, ground, grass, bark, birch, metal, shopGlass | 15 | `SRGB8_ALPHA8` + `RGBA8` + `R8` | albedo (альфа — маска свечения окон), surf (nx, ny, roughness, metalness), ao |
| `cards` 1024² | leaves, roadsign | 2 | `SRGB8_ALPHA8` | albedo с альфа-тестом, растекание цвета под альфу (2 прохода) |
| `signs` 512×128 | 18 вывесок | 18 | `SRGB8_ALPHA8` | текст, альфа из яркости — маска свечения |
| `white` 8², `cloth` 256², `paint` 128² | заглушка, ткань, краска | 1 | `SRGB8_ALPHA8` | только albedo |
| `detail` 256² | зерно | 1 | `RGBA8` | нормаль высокой частоты в RG |

Размеры — при `texSS = 2` (среднее и высокое); на низком все холсты вдвое
меньше по стороне.

Материал (`TX[name]`) — `{ grp, layer, rough, metal, tri }`. Батчи района
хранят имя материала и берут `TX[name]` при каждом вызове, поэтому
пересборка текстур подменяет их разом.

### Как считаются карты

* **Высоты** рисуются той же кистью и с тем же посевом, что и цвет
  (`blotches`, `speckle`, `cracks`, `streaks`, окна) — серее ниже, белее
  выше; зерно (`hnoise`) кладётся в массив, минуя холст.
* **Нормаль** — Собель по замкнутому полю (тайлится), крутизна `bump` в
  описании материала, знак `ny` учитывает, что строки холста идут сверху
  вниз, а ось v — снизу вверх. В шейдере касательный базис строится из
  производных экрана (`perturb`): тангенсов в вершинах нет и не нужно.
  Ориентация проверена синтетическим тестом на тех же функциях.
* **AO** — `1 − clamp((blur(h) − h) × 2.0, 0, 0.85)`, размытие коробочное с
  заворотом, радиус 5 логических пикселей.
* **Roughness** — `база + k_h·(h − 0.5) + k_l·(яркость − 0.5)`; у профлиста
  и ворот шероховатость металла отдельная (`roughMetal`).
* **Metalness** — константа или маска (`metal(x, S)`): лист — металл,
  ржавчина и стёкла — нет.
* **Triplanar** (`tri` — шаг в метрах) — только у коры: три проекции от
  мировых координат, веса `|N|⁴`, нормали проекций в мировые оси.
* **Detail** — RG-нормаль 256² с повторами ×7, вес 0.55 до 6 м и до нуля к
  22 м.

### Цвет

Albedo в `SRGB8_ALPHA8` семплится линейно. Вершинные цвета, тинты, палитры
солнца, неба, тумана и фонарей — авторские, в sRGB — переводятся в
линейное пространство гаммой 2.2 (`lin1`/`lin3`, `pow` в вершинном
шейдере). Тонмаппинг: Рейнхард → плёночный носок → насыщенность →
**кодирование в sRGB** (`pow 1/2.2`). Экспозиция и коэффициенты
`sunK`/`ambK`/`skyK`/`fogK` подобраны по измеренной яркости контрольных
сцен: кадр в целом ±1–4 % от базы, небо светлее на 3–9 %, земля темнее на
1–3 %. Баланс света — этап 03.

## 4a. Свет, небо и окружение

Появилось на этапе 03. Числа — в `QCFG.light`, `QCFG.sky`, `QCFG.env`,
`QCFG.post`; в шейдерах чисел освещения нет.

### Порядок проходов кадра

    [грань кубмапы окружения или уровень префильтра — если солнце сдвинулось]
    → тени: по слою массива глубины на каскад (framebufferTextureLayer),
      только если солнце выше shadow.minAlt — ночью прохода нет вовсе
    → проход глубины в ТУ ЖЕ текстуру, которой пользуется сцена, и заодно
      МАСКА отражающего вторым вложением того же буфера (только там, где
      есть затенение или отражения: мультисэмплинга нет, глубина общая)
    → затенение в складках на половине стороны
      →  размытие с сохранением краёв, два прохода по одной оси
    → отражения в экранном пространстве на половине стороны: марш по лучу
      читает глубину ЭТОГО кадра и цвет ПРОШЛОГО — главный проход чистит
      цвет ниже, а перепроецирует точку попадания матрица прошлого кадра
    → сцена в HDR-буфер (глубина уже посчитана: чистим только цвет,
      depthFunc LEQUAL, ранний z отбрасывает закрытое):
        статика района  →  динамика (тени-блобы, машины, жители)
        →  небо ПОСЛЕДНИМ (полноэкранный треугольник на дальней плоскости,
           depthFunc LEQUAL: под домами шейдер неба не исполняется)
        →  свечения аддитивно
      invalidateFramebuffer(глубина)
    → [resolve мультисэмпла блитом — только там, где он есть: средний профиль]
    → свечение вокруг яркого: порог с уменьшением вчетверо + generateMipmap
    → тонмаппинг в холст: экспозиция, ACES, sRGB; при msaa 0 — с FXAA,
      уровни свечения складываются ДО экспозиции

Смен буфера отрисовки в кадре:

| | смен | какие |
| --- | ---: | --- |
| высокий, день | 11 | три каскада, глубина с маской, затенение, размытие ×2, отражения, сцена, свечение, тонмаппинг |
| высокий, ночь | 8 | глубина с маской, затенение, размытие ×2, отражения, сцена, свечение, тонмаппинг |
| средний, день | 6 | два каскада, сцена, разрешение мультисэмпла, свечение, тонмаппинг |
| низкий, день | 3 | каскад, сцена, тонмаппинг |

Было 8 / 5 / 5 / 3 после этапа 04 и три на всех профилях до него. Свечение
и отражения добавили по одной смене на каждое; маска отражающего досталась
даром — она делит вложение глубины с проходом глубины.

### HDR-буфер

`R11F_G11F_B10F`. Сэмплов на высоком профиле **ноль**, на среднем два —
развилка этапа 04 (см. ниже «Глубина текстурой»); было два везде. Формат и число сэмплов выбраны замером (сцена 01,
высокий, GPU p50; база без HDR 3.92 мс): RGBA16F ×4 10.86 / ×2 6.86 / без
MSAA 5.21; R11F ×4 7.17 / ×2 5.99 / без MSAA 4.93. Расширения
`WEBGL_multisampled_render_to_texture` нет ни в Chromium, ни в WebKit, поэтому
мультисэмпл разрешается блитом через память — там и вся цена.

Подводные камни, на которых буфер молча не собирался и сцена не рисовалась:
у `R11F_G11F_B10F` внешний формат `RGB`, а не `RGBA`; пригодным для отрисовки
его делает `EXT_color_buffer_float`, а не `half_float`.

### Модель отражения

GGX, высотно-коррелированный Smith, Френель по Шлику, Ламберт с сохранением
энергии. Одна функция `directLight` на солнце и на точечные источники.
`F0 = mix(0.04, albedo, metalness)`, шероховатость и металличность из карт,
`vGloss` из вершин — модификатор шероховатости. Интеграл BRDF — аналитическое
приближение Кариса, таблицы BRDF нет.

Точечные источники: спад обратный квадрату с оконной функцией на радиусе и
радиусом самого светильника. Сила выведена приравниванием к прежнему
линейному спаду на восьми и на четырнадцати метрах.

### Небо

Однократное рассеяние Рэлея и Ми, восемь отсчётов по лучу и четыре к солнцу,
плюс приближение многократного рассеяния `(1 − exp(−βR·od))` — без него
горизонт в полдень жёлто-зелёный. Цвет и сила прямого солнца — прозрачность
атмосферы вдоль луча на солнце; палитр солнца, неба, земли и тумана больше
нет. Высота солнца честно уходит в минус, «ночь» считается из неё.

Считается в кубмапу 128² по грани за кадр при сдвиге солнца на 1.5° (при
игровых сутках в 40 минут — раз в десять секунд). Из кубмапы кормятся фон,
туман по направлению взгляда, зеркальные отражения и рассеянный свет.

**Формула живёт в двух исполнениях** — GLSL для кубмапы и JS для сферических
гармоник (кубмапу обратно читать нельзя). Их сходимость проверяет
`tools/sky-test.mjs`: сейчас максимум 0.025 %, в среднем 0.001 %. Тронул
модель — прогони тест.

### Окружение

Префильтр GGX по шести уровням шероховатости, 64² с мипами. Сферические
гармоники L2 считаются на CPU по той же аналитической функции. Материалы
берут рассеянное из гармоник, зеркальное из префильтра, с зеркальной
окклюзией из AO и горизонтной окклюзией.

### Постобработка

Экспозиция по ключевым точкам день/закат/ночь (автоэкспозиции нет намеренно),
ACES, насыщенность, кодирование в sRGB, дизеринг треугольным шумом. Всё —
один раз, в одном проходе.

Свечения-спрайты и светящиеся окна авторские, в экранных единицах: в HDR они
делятся на экспозицию кадра, иначе ночью выбиваются в белое.

## 4b. Тени, затенение и отсев

Появилось на этапе 04. Числа — в `QCFG.cull`, `QCFG.shadow`, `QCFG.ssao`; в
шейдерах чисел нет.

### Отсев статики по клеткам

Район — один меш на материал, отдельных объектов в нём нет, поэтому клетки
живут не в списке объектов, а **в порядке индексов**: `Mesh.cellify`
раскладывает треугольники по сетке 16 м (13×10 = 130 клеток) и переставляет
индексы так, что клетка занимает непрерывный кусок буфера. В кадре остаётся
отметить видимые клетки и слить соседние диапазоны; при наличии
`WEBGL_multi_draw` все диапазоны батча уходят одним вызовом.

Коробки клеток объединены по всем батчам: проверка пирамидой считается один
раз на клетку (130 в кадре), а не на каждый батч (4680). Отсев от этого чуть
мягче, зато на главном потоке не стоит ничего.

Тот же механизм работает в проходе теней: клетки проверяются по осям света
(`Cull.markShadow`), и каскад рисует только то, что может в него бросить тень.

Консервативность проверяет `tools/cull-check.mjs`: кадр рисуется дважды
**внутри одного кадра**, с отсевом и без, и сравнивается попиксельно.
Восемнадцать поворотов камеры в трёх сценах — расхождений ноль. Сравнивать
соседние кадры бесполезно: за кадр жители шагают, зелень качается, и
расходится 80 % пикселей на исправном отсеве.

### Глубина текстурой

Затенению нужна глубина сцены текстурой, и это определило формат буфера.
Замер трёх способов (headed, высокий, GPU p50):

| Сцена | без глубины | блит | проход глубины | без мультисэмпла |
| --- | ---: | ---: | ---: | ---: |
| 02 | 6.88 | 8.41 | 7.47 | **5.21** |
| 03 | 7.92 | 9.09 | 9.32 | **7.53** |

Взят отказ от мультисэмплинга: он дешевле даже исходного состояния, потому
что вместе с мультисэмплом уходит блит разрешения. Сглаживание вернул FXAA в
проходе тонмаппинга — 0.14 мс, отдельного прохода не заводит.

**Мультисэмпловую глубину блитом разрешить можно** — вопреки посылке задания
этапа. На ANGLE/Metal `blitFramebuffer` с `DEPTH_BUFFER_BIT` даёт `NO_ERROR` и
правильные значения (0.62501 при ожидаемых 0.625); запрещён только фильтр
`LINEAR` для глубины. Способ реализован, замерен и отклонён по цене — ключ
`QCFG.post.depthMS`.

**`sampler2DMS` в GLSL ES 3.00 не существует** — это зарезервированное слово,
шейдер с ним не компилируется. Константы `TEXTURE_2D_MULTISAMPLE` в WebGL2
тоже нет.

Порядок в прямом рендере обязывает считать затенение до затенения пикселя,
поэтому проход глубины идёт вперёд — но пишет он в ту же одно-сэмпловую
текстуру, которой потом пользуется сцена: она получает готовый ранний z и
рисуется с `depthFunc LEQUAL` без очистки глубины.

### Каскадные тени

Слои одного `TEXTURE_2D_ARRAY` с `DEPTH_COMPONENT24`; слой выбирается
`framebufferTextureLayer` на одном и том же буфере, отдельного буфера на
каскад нет. Границы 14 / 42 / 120 м. Профили: низкий 1 каскад 512², средний
2 по 1024², высокий 3 по 1024² (1 / 8 / 12 МиБ).

Каскад накрывает срез пирамиды **шаром**, а не коробкой: шар не зависит от
поворота камеры, поэтому при развороте размер каскада не дышит. Центр шара
привязан к сетке в пространстве света с шагом ровно в тексель каскада — это
и убирает дрожание при ходьбе. Плотность: 0.031 / 0.093 / **0.188** м на
тексель (дальняя граница ужата со 120 до 85 м на этапе 05, радиус третьего
каскада 136 → 96 м).

**Каскад выбирается по расстоянию**, а не по попаданию в квадрат. Так можно:
шар строился вокруг среза пирамиды, поэтому всё видимое ближе его границы
заведомо внутри квадрата. Зато у отсева появляется право сказать «приёмники
этого каскада — только его шар», и тенеобразующие отбираются по ДЛИНЕ ТЕНИ:
точка на высоте y роняет тень на y/sin(высоты солнца) вдоль луча, а высота
каждой клетки уже лежит в её коробке (`Cull.markShadow`, ключ
`shadow.casterCull`). До этапа 05 проверки вдоль луча не было вовсе, и при
солнце в 14° ближний каскад радиусом 16 м отмечал 45 клеток из 130 — шахту
через весь район, которую потом отсекали плоскости ортопроекции.

Дальняя граница теней — общая на все каскады, а не свойство последнего.

Выборка сравнивающая (`COMPARE_REF_TO_TEXTURE` + `LINEAR` — аппаратный PCF
2×2 в одном обращении), поверх неё сетка 3×3, то есть фильтр 6×6 текселей за
девять выборок. Координаты каскада `highp`: в `mediump` на Apple это
половинная точность, и сто метров района кладутся с шагом в дециметр.

Смещений три, потому что и ошибок три: постоянное (квантование глубины),
наклонное с потолком (тексель накрывает тем больший перепад, чем косее свет;
у ребра tan уходит в бесконечность) и нормальное (сдвиг точки выборки вдоль
нормали в долях текселя — снимает рябь, не поднимая тень над землёй).
Значения найдены перебором `tools/shadow-check.mjs --bias`; окно узкое и
лежит низко — 0.00045 / 0.0010 / 0.22.

Ночью прохода нет вовсе: солнце ниже `shadow.minAlt` — ни отрисовки, ни смены
буфера, а `uShadowK = 0` закрывает ветку выборки. В разборе кадра по проходам
у ночных сцен строки `shadow#0` попросту нет.

Стабилизация проверена счётом (`--stab`): каскад ставится так, будто камера
сдвинулась на полметра, а вид остаётся прежним. С привязкой к сетке
расходится 0.017–0.019 % пикселей, без неё 0.66–1.01 % — в 35–55 раз больше.

### Затенение в складках

Половина стороны буфера сцены, R8, двенадцать отсчётов в полусфере вокруг
нормали, ядро повёрнуто на каждый пиксель. Нормаль — из производных
восстановленной позиции, отдельного буфера нормалей нет; позиция
восстанавливается двумя тангенсами поля зрения, а не обратной матрицей.
Размытие с сохранением краёв: вес по перепаду глубины, **два прохода по
одной оси** (этап 05: одно ядро 5×5 брало 25 отсчётов затенения и 25 глубины
на пиксель — столько же, сколько стоил сам расчёт; два прохода берут 10 и 10
и выигрывают 0.10–0.19 мс во всех четырёх парных прогонах, а картинка
расходится на 0.06 % пикселей). Пинг-понг идёт между теми же двумя буферами.

Половинное разрешение — выигрыш 0.72–1.16 мс, проверено четырьмя парными
прогонами вперемешку.

### Куда что умножается

Это первое место, где легко посчитать одно и то же дважды:

| Слой | Что умножает |
| --- | --- |
| Тень от солнца | **только** солнечный член (`directLight` с `uSunDir`) |
| Отражения в экранном пространстве | подменяют собой НЕБО из префильтра, а не ложатся поверх: дальше идёт та же формула с `envBRDF` и зеркальной окклюзией |
| Свечение вокруг яркого | складывается с кадром в линейном свете ДО экспозиции, поэтому проходит через ACES вместе со всем остальным |
| Затенение в складках | рассеянное из гармоник и зеркальную окклюзию |
| Карта AO материала | то же плюс солнце (через `light.sunAO`) и точечные источники |
| Вершинное затенение низа | цвет вершины, то есть всё сразу |

Три слоя затенения разведены по масштабам: карта AO — мелкий рельеф
материала, вершинное — градиент на 3.5 м вверх по стене, экранное — первые
полметра у стыка. Перекрываются только в нижней шестой части рампы, поэтому
вершинное убавлено с 0.17 до 0.12, а не убрано.

Тени-блобы гаснут до 0.55 там, где работает настоящая тень (первые два
каскада, 42 м), и возвращаются к полной силе за каскадами и ночью.

## 4c. Свечение вокруг яркого и отражения в экранном пространстве

Появилось на этапе 05. Числа — в `QCFG.bloom` и `QCFG.ssr`; в шейдерах чисел
нет.

### Свечение (bloom)

Считается в ЛИНЕЙНОМ свете, ДО экспозиции и тонмаппинга: только там оно
физично — яркое расплывается по кадру и тянет за собой тонмаппинг, а не
подмешивается плёнкой поверх готовой картинки.

Устройство: один проход порога с уменьшением вчетверо по стороне, дальше
`generateMipmap`, дальше сложение уровней в проходе тонмаппинга. **Цепочки
буферов «вниз-вверх» нет** — радиус даёт мип-цепочка одной текстуры. Это
решение не про красоту, а про смены буфера отрисовки: четыре уровня
отдельными буферами стоили бы восьми смен при уже имевшихся восьми.

* **Порог** с мягким коленом: жёсткий даёт ступеньку на градиенте неба, а
  порог около нуля превращает дневной кадр в молоко. Значение 0.6 — в
  линейном свете до экспозиции, то есть привязано к тому, где насыщается
  ACES, а не к единице.
* **Уменьшение** — тринадцать отсчётов, а не четыре: четырьмя одиночная
  яркая точка проскакивает между отсчётами и свечение мерцает на движении.
  Шаг отсчётов растёт вместе с шагом уменьшения.
* **Веса уровней** — единица на каждый, нормировано к сумме. У точечного
  источника уровень l держит ту же энергию, размазанную вчетверо шире и
  вчетверо слабее, поэтому равные веса дают правильный спад от центра.
* **Выборок меньше, чем уровней** (`taps` 3 против `levels` 6):
  `LINEAR_MIPMAP_LINEAR` смешивает два соседних уровня в одном обращении, и
  дробный уровень 0.5 — это полусумма нулевого и первого. Тонмаппинг идёт
  по полному кадру 2880×1800, и каждая лишняя выборка там — пять миллионов
  обращений к памяти.
* В проходе с постфильтром сглаживания свечение берётся ОДИН раз и
  передаётся во все пять вызовов `grade`: оно самая низкая частота в кадре,
  и четырём соседям постфильтра оно одно и то же.

Профили: на низком свечения нет, на среднем и высоком есть.

### Отражения (SSR)

Марш луча отражения по буферу глубины, цвет из буфера сцены. Смешивание с
небом делает ГЛАВНЫЙ проход — в той же строке, где он берёт префильтр
окружения: `skyRad = mix(skyRad, ssr.rgb, вес)`, а дальше идёт та же формула
с `envBRDF` и зеркальной окклюзией. Поэтому лужа отражает дом ровно с той
силой, с какой она отражала бы небо, а где луч ни во что не попал —
уверенность ноль и остаётся небо, без видимой границы.

**Порядок в кадре.** Проход отражений идёт ДО главного, рядом с затенением:
глубина уже посчитана проходом глубины, а в `HDR.tex` ещё лежит ПРОШЛЫЙ
кадр — главный проход чистит цвет позже. Точка попадания перепроецируется
матрицей прошлого кадра (`uReproj = prevViewProj · inv(view) · flipZ`),
поэтому поворот камеры отражение не размазывает.

Почему не иначе: писать маску отражающего вторым вложением ГЛАВНОГО прохода
— лишняя полоса памяти на самом дорогом проходе кадра; складывать отражение
поверх готового кадра в тонмаппинге — там не известны ни шероховатость, ни
Френель, и смешать с небом нечем.

**Маска отражающего** — то, на чём держится цена. Марш по лучу по всему
кадру стоил бы больше всего остального; маску пишет проход глубины ВТОРЫМ
ВЛОЖЕНИЕМ того же буфера (у него та же текстура глубины, поэтому смен
буфера не прибавилось, а цвета он не писал вовсе). На контрольных сценах
маска покрывает 12–17 % кадра, попадание даёт 0.4–1.9 %.

Глянцевость для маски берётся из вершин И из материала: витринное стекло
гладкое картой шероховатости (0.14), а `vGloss` у него ноль — маска по
одному `vGloss` пропустила бы все витрины.

**Нормаль** восстанавливается из производных глубины, своего буфера
нормалей нет. На силуэте это врёт: соседний отсчёт лежит на другом объекте,

Разрыв глубины больше сотой доли расстояния — не поверхность, а край.

**Порог шероховатости 0.45.** Лужа днём имеет
rough = 0.80·(1 − 0.72·0.85) = 0.31, ночью 0.12 (`glossNight` делает

### Авто-масштаб

**В настоящем браузере контроллер не срабатывает.** Headed, высокий профиль,
40–45 с на сцену: пропущенных кадров ноль, шагов контроллера ноль, буфер
остаётся 2880×1800. Перепроверено на этапе 05 после того, как в кадр
добавились свечение и отражения: сцена 03 — GPU 10.69 мс, ноль шагов, ноль
пропусков; сцена 05 — 11.60 мс, ноль и ноль.

**В headless контроллер срабатывает ложно** — и это не артефакт замерной
обвязки, а поведение самого контроллера. Проверено инструментом, который
телеметрию не ставит вовсе и отдаёт таймер игре: на сцене 03 двенадцать
шагов вниз до 0.6, на сцене 05 девять шагов до 0.675 — при GPU 5.1–6.5 мс,
то есть вдвое ниже бюджета. Причина в ветке подстраховки:

```js
if (dropped && this.gpuAvg > budget * 0.5) { over = true; }
```

В headless интервалы rAF гуляют от 7 до 26 мс, доля «пропущенных» кадров
11–12 %, и они кучкуются; четырёх подряд хватает на шаг вниз. Ворота
`gpuAvg > budget/2` на высоком профиле открыты (6.4 против 5.5), на среднем
закрыты (3.6 против 5.5) — поэтому на среднем в том же headless масштаб не
двигается. В браузере с вертикальной синхронизацией пропусков нет вовсе (за
45 с — ноль), и ветка не срабатывает.

**Практический вывод:** проверять авто-масштаб только в headed и только
через `tools/scale-probe.mjs`; цифры буфера из `perf-probe --dynamic=1` в
headless ничего не значат.

## 7. Разбор кадра по проходам и как он мерялся

**Способ — префиксы по таймер-запросам.** Один `TIME_ELAPSED_EXT` на кадр,
от начала кадра до конца прохода k; k перебирается по кадрам; цена прохода —
разность медиан соседних префиксов. Искусственная граница запроса в каждом
замере одна и примерно одинаковая, поэтому в разности она сокращается.
Последний префикс равен кадру целиком и сходится с обычным замером в пределах
4 % — встроенная проверка метода. Слот k = −1 меряет пустой префикс. Рядом
печатается межквартильный размах: проход дешевле него уходит в разности в
минус, и так и печатается.

**Чего делать нельзя.** Прямой способ — запрос на каждый проход — на M4 даёт
мусор: шесть запросов в кадре показали сумму 32 мс при кадре 4.4 мс, а
«очистка» из одного `gl.clear` — 1.8 мс. Каждая граница запроса заставляет
тайловый GPU сохранить буфер 2880×1800 в память и загрузить обратно. `readPixels`
на границах проходов ломается по той же причине и остаётся только запасным
способом для WebKit, где таймера нет вовсе (там разрешение таймера 1 мс и
таблица бесполезна).

**Программы опознаются по метке** `/* PASS:имя */` в исходнике шейдера.
Сейчас их одиннадцать: `main` в двух вариантах (день и ночь), `sky`, `glow`,
`tone` в четырёх сборках (со сглаживанием и без, со свечением и без),
`env` в двух (кубмапа неба и префильтр), `depth`, `shadow`, `ssao`,
`ssaoblur` в двух (одно ядро и разделяемое), `bloom`, `ssr`.

**Первый измеряемый проход кадра завышен, и это не шум.** Цена прохода —
разность медиан соседних префиксов, и всё, что тянется из предыдущего кадра,
попадает в первый участок этого. Днём первый участок — проход теней, ночью
теней нет, и первым оказывается проход глубины. Проверено прямо (этап 05):
на сцене 04 проход глубины стоит 0.635 мс как есть и 0.174 мс, если
включить проход теней ночью через `--cfg='{"shadow":{"minAlt":-90}}'` —
сцена та же, геометрия та же, проход глубины не менялся. Читая таблицу,
первую строку кадра надо считать «этот проход плюс хвост предыдущего кадра»,
а не ценой прохода.

Разбор кадра, высокий профиль, медианы разностей префиксов, мс. Все каскады
идут одной программой подряд, поэтому в строку `shadow#0` попадает весь проход
теней целиком — разделить их этим методом нечем:

| Сцена | статика | глубина | тени | затенение | размытие | отражения | свечение | тонмаппинг | небо |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 01 | 2.11 | 0.15 | 0.84 | 0.91 | 0.38 | 0.44 | 0.31 | 1.27 | 0.12 |
| 02 | 2.37 | 0.68 | 0.81 | 0.81 | 0.38 | 0.42 | 0.31 | 1.11 | −0.03 |
| 03 | 2.40 | 0.43 | 0.81 | 0.74 | 0.38 | 0.42 | 0.25 | 1.03 | 0.08 |
| 04 · ночь | 2.09 | 0.63 | **нет** | 0.94 | 0.41 | 0.43 | 0.20 | 1.25 | 0.21 |
| 05 · ночь | 2.39 | 0.93 | **нет** | 1.01 | 0.43 | 0.37 | 0.29 | 0.96 | −0.01 |

Свечение и отражения стоят по отдельности: свечение — 0.20–0.31 мс на свой
проход (порог с уменьшением плюс `generateMipmap`, своей программы у него
нет) и около 0.15 мс в тонмаппинге на три выборки, итого 0.35–0.45;
отражения — 0.37–0.44 мс на марш по лучу.

Отсутствие строки `shadow` у ночных сцен — это и есть доказательство, что
ночью проход теней не исполняется.

Цена каскадов получена грубее, перебором их числа (сцена 03, headed): ноль
каскадов 9.29, один 9.84, два 9.94, три 9.86 мс. Весь проход теней стоит
около 0.6 мс, второй и третий каскад в разности не различимы.

Проход окружения (грань кубмапы или уровень префильтра) появляется раз в
десять секунд игрового времени и в медиану не попадает.

## 9. Расширения WebGL2

| Расширение | Chromium 151 / M4 | WebKit 26.5 / M4 | Зачем |
| --- | :---: | :---: | --- |
| `EXT_texture_filter_anisotropic` | есть (max 16) | есть (max 16) | анизотропия из профиля, 4/8/16 |
| `EXT_disjoint_timer_query_webgl2` | **есть** | **нет** | время GPU для авто-масштаба и замера; в WebKit авто-масштаб живёт на интервалах кадра |
| `EXT_color_buffer_float` / `_half_float` | есть | есть | HDR-буфер, если понадобится этапу 03 |
| `OES_texture_float_linear` | есть | есть | |
| `WEBGL_debug_renderer_info` | есть | есть | `pickDefault` узнаёт GPU |
| `KHR_parallel_shader_compile` | есть | есть | при трёх программах не нужно |
| `WEBGL_multi_draw` | есть | есть | схлопнуть батчи района |
| `WEBGL_compressed_texture_s3tc` / `_astc` / `EXT_texture_compression_bptc` | есть | есть | не используются: кодировщик пришлось бы тащить в файл |

Пределы: `MAX_TEXTURE_SIZE 16384`, `MAX_SAMPLES 4`, `MAX_VARYING_VECTORS 30`.

Всё, что этап 02 использует сверх ядра WebGL2, — анизотропия и таймер —
проверяется при запуске и деградирует без ошибок: без анизотропии дорога
вдаль мылится, без таймера авто-масштаб считает пропуски кадров.

Настоящий Safari (не WebKit из Playwright) по-прежнему не снят: процедура —
`tools/ext-probe.js` в консоль веб-инспектора, пять минут.

  `WEBGL_multi_draw`.
* **Кадр.** WebKit держит ровные 17 мс (58.8 FPS, p95 17–18 мс) во всех
  сценах и в обоих прогонах — развёртка 60 Гц. Chromium в headless-режиме
  не привязан к развёртке, поэтому его FPS сравнивать с WebKit нельзя; по
  GPU-таймеру кадр в Chromium стоит 2.3–3 мс на среднем профиле, то есть в
  четыре-пять раз дешевле развёртки. Гипотеза этапа 00 про дорогие смены
  состояния через ANGLE→Metal не подтвердилась и не опровергнута: разложить
  кадр WebKit по проходам нечем.
* **Загрузка.** Генерация текстур в WebKit быстрее на 15–20 % (canvas 2D у
  него дешевле), остальное совпадает.

## 11. Узкие места, по убыванию стоимости

1. **Статика района** — 2.1–2.6 мс, по-прежнему самый дорогой проход, и
   теперь уже с большим отрывом. Отсев по клеткам снял с него около трети на
   этапе 04; дальше его удешевит только меньше пикселей или меньше материалов
   на кадр.
2. **Тонмаппинг** — 1.0–1.4 мс: полноэкранный проход по 2880×1800, и в нём
   теперь и сглаживание, и сложение свечения. Каждая выборка там стоит пяти
   миллионов обращений к памяти — поэтому уровней свечения шесть, а выборок
   три (`bloom.taps`).
3. **Затенение в складках** — 0.87–1.01 мс. Размытие рядом с ним стоит уже
   0.27–0.36 (было столько же, сколько сам расчёт), после того как стало
   двухпроходным.
4. **Свечение и отражения** — 0.15–0.20 и 0.39–0.44 мс. Отражения держатся
   на маске: без неё марш по лучу шёл бы по всему кадру и стоил бы больше
   всего остального вместе взятого.
5. **Разрешение мультисэмпла блитом** остаётся только на среднем профиле;
   на высоком мультисэмплинга больше нет, и вместе с ним ушёл блит.
   Расширения `WEBGL_multisampled_render_to_texture` нет ни в Chromium, ни в
   WebKit.
6. **Ночной цикл по восьми источникам** — днём его нет вовсе (отдельный
   вариант программы).
7. **Свечения-спрайты не стоят ничего** — этап 05 проверил это прямо,
   выключив проход вместе с вызовами (`QCFG.glow.on`): разница в пределах
   шума на обоих профилях, днём и ночью. Прежняя оценка «0.66–1.02 мс»
   относилась к разрешению мультисэмпла, попадавшему в тот же сегмент.
8. **Генерация текстур** — 593 мс до конца сборки района, конец заставки
   702 мс.
9. **Главный поток свободен** (<1 мс), JS оптимизировать незачем.

Что уже в порядке и трогать не надо: плотность пикселей и масштаб под
контролем профилей; батчи по материалу; все текстуры с мипами и
анизотропией; персонажи скиннятся на GPU; интерфейс в полной плотности
отдельно от сцены; тонмаппинг ровно один; проход неба стоит 1.5–4.7 % кадра
и считается только там, где небо видно.

## 12. Что дальше

1. **Статика района — единственное крупное место, где ещё есть деньги.**
   2.1–2.6 мс из 8.7–10.0. Отсев уже снял треть; дальше — либо меньше
   материалов на кадр (батчей 15, смен группы текстур меньше, но всё же),
   либо меньше пикселей.
2. **Отражения видят мало.** Отражающего в кадре 12–17 % по маске, а
   попадание луча даёт 0.4–1.9 %. Лужи мелкие и расставлены случайно
   (`Math.random` в размещении, а не посев), стёкла отражают небо, потому что
   смотрят вверх. Чтобы отражения читались, нужен не марш получше, а больше
   мокрого: например, гладкая полоса вдоль лотка (`plate` уже принимает
   `gloss`, и никто его не передаёт).
3. **Разбор кадра по проходам врёт на первом проходе кадра.** Первый
   измеряемый участок забирает в себя хвост предыдущего кадра: ночью, когда
   прохода теней нет, его забирает проход глубины (0.635 против 0.174 мс на
   той же сцене с включёнными ночью тенями). Метод не чинится — чинится
   чтение таблицы.
4. **Отсев по клеткам мягче, чем мог бы**: коробки объединены по всем батчам
   ради дешёвой проверки. Раздельные коробки дали бы более точный отсев ценой
   работы на главном потоке, где запас есть.
5. Проверить полосы на ночном небе количественно уже на гладкой модели:
   прежняя проверка делалась на старом fbm-небе.
6. Снять настоящий Safari через `tools/ext-probe.js`.
7. Посторонняя находка этапа 03: текст вывесок на фасадах со стороны
   `side: 'S'` читается зеркально. К рендеру отношения не имеет.
